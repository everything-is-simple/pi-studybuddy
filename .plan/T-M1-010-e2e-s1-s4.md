## 2. 架构决策：E2E 框架选择

### 2.1 决策：采用 vitest + Electron 直接启动模式（非 Playwright）

**决定**：E2E-01~03 使用 vitest + Electron `_electron.launch()` 模式，不引入 Playwright。

**依据**：
1. **08-Test §6 要求 Playwright**，但 §1.3 第 6 条"不连真实外部服务"是铁律——E2E 本质是"真实 Electron + 真实数据层 + mock 外部服务"，不是"真实浏览器 + webServer"
2. **pi-desktop 范式**：pi-desktop 的 E2E（`scripts/test-browser-agent-e2e.mjs`）用 Electron 直接启动 + assert，不依赖 Playwright
3. **ai-studybuddy 范式不适用**：ai-studybuddy 是前后端分离（FastAPI + Vite webServer），其 Playwright config 用 `webServer` 启动后端——pi-studybuddy 是 Electron 单体，没有独立后端
4. **AGENTS.md §6.4 禁止过度工程化**：引入 Playwright 需要新增 `@playwright/test` 依赖 + 浏览器下载 + Electron 桥接配置，而 vitest 已就绪
5. **vitest 已能覆盖**：vitest + `_electron.launch()` 可启动真实 Electron 窗口，通过 `webContents.executeJavaScript` 驱动 UI 交互，通过 RPC 通道验证数据层
6. **依赖最小化**：不新增 devDependencies，沿用 vitest + electron

**权衡**：
- 牺牲了 Playwright 的 `page.getByRole/page.getByLabel` 等语义选择器
- 改用 `webContents.executeJavaScript` + DOM querySelector 驱动交互
- 保留 08-Test §6.1 的"真实 Electron 启动 + 全链回归"核心要求

### 2.2 备选方案（记录但不采用）

- **方案 B：Playwright Electron 模式**（`@playwright/test` + `_electron.launch()`）
  - 优点：08-Test §6 明确要求 Playwright；语义选择器更强大
  - 缺点：新增 `@playwright/test` devDependency + 浏览器下载（~100MB）+ Electron 桥接配置；与 vitest 两套测试框架并存
  - 不采用原因：AGENTS.md §6.4 禁止过度工程化；vitest 已能满足"真实 Electron + 全链回归"要求

> **注**：本决策需用户审查批准。若用户坚持 Playwright，则改用方案 B，但需接受新增依赖。

## 6. 风险与对策

### 6.1 Electron 启动在无显示环境失败

**风险**：CI/agent 环境无显示，Electron 启动失败。

**对策**：
- Windows 环境有显示（用户本机），可直接启动
- 若需 CI，加 `--headless` 或虚拟显示（v0.1 不考虑 CI）
- E2E 仅在用户本机运行，不阻塞 unit/smoke

### 6.2 RPC 通道驱动 UI 交互复杂

**风险**：通过 `webContents.executeJavaScript` 驱动 UI 交互比 Playwright 的 `page.click()` 复杂。

**对策**：
- E2E 侧重"数据层全链回归"，UI 交互断言最小化
- 关键断言通过 RPC 调用验证数据状态，不依赖 UI 渲染
- UI 交互仅验证"Tab 切换 + 按钮点击触发 RPC"

### 6.3 mock 注入点

**风险**：E2E 需要真实数据层 + mock 外部服务，mock 注入点需要设计。

**对策**：
- 业务 handler 已支持可注入 Adapter（MockExamGenerator/QuestionGenerator/ReportPolisher 等）
- E2E 通过环境变量或 RPC 参数注入 mock 标记
- 不修改 handler 代码，通过测试夹具的 Adapter 注入
