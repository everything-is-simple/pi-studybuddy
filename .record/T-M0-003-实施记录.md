## 3. 偏差

- **计划（开工 prompt）原拟**：credential-vault 直接复用 pi-desktop 的 `channel:xxx` handler 模式。实现确认 06-API §3.15 契约 `credentials.set` 的 value 为 `string`（非 pi-desktop 的对象），故 CredentialVault 的 value 统一按 `string` 处理，与 06-API 契约对齐。
- **测试需 mock electron**：`src/main/credential-vault.ts` 首行 `import { safeStorage } from "electron"`（INV-04 断言要求），vitest(Node) 无 Electron 运行时，单件测试顶层 `vi.mock("electron", ...)` 使 import 安全加载，功能测试经构造注入 fake safeStorage 覆盖默认实现。
- **CV-02 断言修正**：磁盘存的是 base64（解密后才含加密前缀串），首版断言误对原始文件内容匹配 `pseudocrypt:` 失败，修正为解码 base64 后断言。

## 4. 问题及根因

- **vitest 无法加载 electron 模块**：`import { safeStorage } from "electron"` 在 Node 测试环境直接 import 会失败。根因：electron 是桌面运行时模块，非 Node 内置。解决：`vi.mock("electron")` 顶层 mock + 构造注入 SafeStorageAdapter 接口解耦。
- **CV-02 base64 断言误判**：磁盘 entries 存的是加密后 base64（`cHNldWRvY3J5cHQ6...`），首版测试对原始文件 JSON 匹配 `/pseudocrypt:/` 失败。根因：忽略了 set 时 `encrypted.toString("base64")` 已编码。解决：`JSON.parse(raw).entries[key]` 取 base64 再解码断言。

## 5. 关键决定及依据

- **构造注入 SafeStorageAdapter（默认 electron safeStorage）**：满足 INV-04（首行 import）同时解耦测试。依据：03-Arch §4.5（`import { safeStorage } from "electron"`）+ 08-Test §5.6 冒烟可在 Node 单件环境验证。
- **value 统一为 string**：06-API §3.15 `credentials.set` 契约 `value: string`。依据：06-API §3.15 权威条款（不偏离已批准契约到 pi-desktop 的对象形态）。
- **键名校验抛错而非静默**：非法键（缺前缀/错误前缀/超长/非法字符）一律抛错，defense-in-depth。依据：01-TRD §9.2 键名匹配 + 03-Arch §4.5 严格校验。
- **加密不可用即抛错且不落盘**：`assertAvailable()` 在 set/get 前校验，不可用抛错且不写文件。依据：安全降级，避免明文落盘（08-Test §5.6 + AGENTS.md §9.3 日志/存储脱敏语义）。
- **Windows chmod best effort**：Windows 上 chmod 0o600 语义受限，writeFileSync 已带 mode 0o600 + rename 后 chmod 包 try/catch。依据：03-Arch §4.5（原子写 temp+rename + mode 0o600，兼容 pi-desktop 范式）。
