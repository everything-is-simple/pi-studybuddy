## 5. 关键决定及依据

### D1：Tab 组件接收预加载数据 props（非 useEffect 异步加载）

**决定**：Tab 组件通过 props 接收已加载的业务数据（dailyBrief/materials/note/modules/questions/result/mistakes/weakPoints），而非组件内部 useEffect 调用 RPC。

**依据**：
- renderToStaticMarkup 是同步的，无法处理 useEffect 异步加载
- 纯展示组件更易于测试（直接传入夹具数据断言渲染输出）
- 符合 React 最佳实践（展示组件与容器组件分离）
- 运行时由父组件（AppShell 或后续任务）加载数据后传入

### D2：TypedRpcClient 基于 Api 契约类型化

**决定**：rpc-client.ts 创建 TypedRpcClient 接口，call 方法基于 Api 契约（api.ts）提供 params/result 类型推导。

**依据**：
- 03-Arch §6.2 renderer 技术栈
- 06-API §1-§3 Api 契约已就绪
- 类型化 call 方法减少运行时错误

### D3：不引入新依赖（jsdom/@testing-library/react/zustand/react-markdown）

**决定**：沿用 T-M0-008 的 renderToStaticMarkup 静态渲染测试范式，不引入新依赖。

**依据**：
- AGENTS.md §6.4 禁止过度工程化
- 计划明确不引入新依赖
- 静态渲染测试足以覆盖关键断言（防泄露/隐私边界/六分类/AI 标记）
