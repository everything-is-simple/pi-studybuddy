## 4. 问题及根因

### 4.1 Electron 生产 SQLite 断裂

Electron 33.4.11 内嵌 Node 20.18.3 不提供 `node:sqlite`，而 `src/data/sqlite.ts` 直接读取 `process.getBuiltinModule("node:sqlite").DatabaseSync`。因此实际 Electron 主进程启动时抛出 `TypeError: Cannot read properties of undefined (reading 'DatabaseSync')`，`global.db` 无法初始化。既有 E2E 使用系统 Node 22+ 子进程，未覆盖此生产差异；本次迁移后业务 E2E 与生产主进程均由真实 Electron 承载。

### 4.2 sandbox preload 相对模块不可加载

真实 BrowserWindow 使用 sandbox preload。编译后的 preload 若 `require("../shared/constants")`，在 Electron sandbox preload 中不属于允许加载的模块，导致 `window.piBridge` 未建立。修复为 preload 内部同步 IPC 通道表，保持与共享常量一致并用真实桥面断言验证。

### 4.3 utility process 端口竞态与重复连接

主进程在 utility process `spawn` 时立即转移 MessagePort，早于 agent-host listener 注册，导致端口未附着；补充 `{type:"ready"}` 握手和 pending queue 后解决。随后发现生产 renderer 初始化已调用一次 `connectHost()`，探针第二次调用会被 host 的单端口附着保护忽略；preload 改为缓存首次连接端口后，业务连接与验收探针共享同一生产端口。

## 5. 关键决定及依据

1. **选择升级 Electron，而非替换 SQLite Adapter。** 依据是当前数据层已使用 Node 原生 `node:sqlite` / `DatabaseSync`，Electron 36.9.5 的嵌入 Node 22.19.0 已提供同一原生能力；这条变更最小、保持既有数据模型与适配器契约，不引入新的 SQLite 原生依赖或 mock fallback。
2. **精确锁定 `electron@36.9.5`。** 避免 caret 漂移；这是本次实测通过 `node:sqlite` 的稳定线，并满足项目 Node 22+ 运行时要求。
3. **保留生产 sandbox。** 测试仅在 headless Windows 启动命令增加 `--no-sandbox`，没有放宽 BrowserWindow 的 `sandbox: true` 或其他安全配置。
4. **将业务 E2E harness 全量迁移到真实 Electron。** 旧的 Node.js 子进程承载路径会掩盖 Electron 内嵌 Node/SQLite 差异，不能继续作为业务 E2E 入口；现由真实 Electron 主进程运行 fixture，并通过仅监听 127.0.0.1 的 TCP JSON-lines 通道与测试驱动器通信。
5. **不改 toolchain 已验证版本阈值。** 默认 Node25 的失败是环境政策信号，不是本任务通过修改阈值消除的测试失败；Node24.14.0 是项目认可的复验环境。
