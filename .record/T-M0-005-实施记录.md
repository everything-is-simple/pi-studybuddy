## 3. 偏差

### 3.1 changeType 推断策略：WatchEntry 级 → per-target TargetState

**计划**：`WatchEntry` 含 `lastExists: boolean` 字段，单个 entry 跟踪一个状态。

**实际**：`WatchEntry.targets: Map<targetPath, TargetState>`，每个变更目标独立跟踪 `lastExists`。

**原因**：目录监听场景下，单个 `WatchEntry` 需要跟踪目录内多个子文件的独立存在状态。若用单一 `lastExists`，目录内 A 文件新增（lastExists=true）后 B 文件删除会被误判为 "change"（因 lastExists 仍为 true）而非 "unlink"。

**影响**：实现复杂度略增，但语义正确性显著提升。计划 §4.2 的 WatchEntry 接口已相应调整。

### 3.2 FW-UNIT-09 测试用例移除

**计划**：FW-UNIT-09 测试 "start 非文件/非目录路径 → 抛错 not watchable"。

**实际**：移除该测试，后续用例重编号（原 FW-UNIT-10 防抖测试改为 FW-UNIT-09）。

**原因**：跨平台无法稳定构造非文件/非目录路径（FIFO/socket 在 Windows 需管理员权限），该分支为防御性代码，不阻塞契约覆盖。

**影响**：单件测试数 14 不变（原 15 计划减 1 后重编号），覆盖完整性不受影响。

## 4. 问题及根因

| 问题 | 根因 | 修复 |
|---|---|---|
| FW-UNIT-11（目录新增文件 → add）在 Windows 失败 | Windows fs.watch 对新文件创建发 "change" 而非 "rename"，eventType 信号不可靠 | 改用 per-target lastExists 跟踪：新 target 默认 lastExists=false，stat 成功 + lastExists=false → "add" |
| FW-RPC-04（目录监听 add 事件）偶发不稳定 | 目录监听启动后立即写入文件，watcher 可能未就绪 | 测试增加 80ms 启动等待 + 150ms 防抖等待 |
| contract-coverage 报告 files.watch/unwatch missing | 静态 AST 扫描无法解析 `...createFileHandlers(fileWatch)` spread 注册 | 已知限制（与 toolchainHandlers 一致），非阻塞，实际运行时已注册 |

## 5. 关键决定及依据

| 决定 | 依据 |
|---|---|
| per-target TargetState 跟踪 lastExists | Windows fs.watch eventType 不可靠 + 目录监听需独立跟踪多个子文件状态 |
| 单文件监听预填 lastExists=true | 文件已存在，首次事件应为 "change" 而非 "add" |
| 目录监听 targets 初始空 + 新 target 默认 lastExists=false | 目录内潜在新增文件首次出现应为 "add" |
| Stream 订阅 key 始终为 watchedPath | 便于订阅者按目录订阅接收全部子文件事件（06-API §4 语义） |
| 不修改 check-desktop-security.mjs | file-watch 不新增 08-Test §5.7 安全不变量（六条均与 file-watch 无关） |
| 不实现 file-access 权限检查 | 后续安全任务（pi-desktop assertAllowed 范式） |
| 递归监听失败回退非递归 | 跨平台兼容（Linux 部分版本不支持 recursive:true） |
