# M5 全面测试阶段提示词：系统交互、错误边界与真实数据治理审计

> **资产类型**：受控治理 / 审计提示词。
>
> **不是执行计划**：本文件不创建任务、不改变 Todo 状态、不替代唯一 `.plan/`，不授权业务代码、数据库迁移、commit、merge、push，也不自动启动 T-M5-005~008。
>
> **当前用途**：为 T-M5-004 的 S1-S5 验收提供系统级方法，并把超出 T-M5-004 的发现转成明确的范围裁决或后续任务输入。
>
> **快照日期**：2026-08-13。所有 Git、任务、测试和文件事实必须以实时仓库为准，本文静态内容不覆盖 live SoT。

## 0. 这份提示词要解决的问题

当前系统已经经历了需求分析、业务设计、架构设计、前端实现、后端实现和多轮测试。但前后端实施过程中曾出现过“页面先完成、后端后补；一个完整 phase 之后才补足链路”的问题。

这说明当前主要风险不再只是某一个按钮有没有 action，而是**系统的可验收性没有被统一建模**：

1. 我们是否知道用户与系统之间一共有多少种有业务意义的交互动作？
2. 每个动作是否都有明确的前置条件、成功结果、失败结果、禁用条件、重试方式、取消方式和重启后行为？
3. 每种错误发生在哪一层，应该由哪一层负责分类、转换、展示、记录和恢复？
4. 每个动作产生的数据，哪些是业务事实必须真实持久化，哪些只是派生结果、运行态、缓存或测试数据？
5. UI 外观、Electron 运行承载、RPC 契约、业务逻辑、功能模块、SQLite / 文件数据和测试证据之间，是否有可追踪的责任边界？
6. 测试是否证明了真实产品，而不是只证明 mock、fixture、renderer 注入或测试后门？

**本提示词的核心目标**：把系统从“功能已写、测试数量很多”提升为“每个用户动作都可解释、可验证、可恢复、可追踪、可持久化或明确不持久化”。

## 2. 分层模型：把外观、运行、逻辑、功能和数据切开

审计必须按下列责任层分析，不允许用“前后端都做了”作为完成证明。

### 2.1 外观层 UI / Presentation

负责：

- 页面布局、控件、文字、图标和可访问名称；
- loading、empty、success、error、retry、disabled、readonly、archived、confirm、cancel 状态；
- 用户能否看懂当前状态和下一步动作；
- 不展示内部错误栈、路径、完整 UUID、SQL、密钥或学生隐私原文。

不负责：

- 自行伪造业务成功；
- 自行决定事实状态；
- 绕过 RPC 直接写数据库；
- 把内部异常对象直接显示给用户。

### 2.2 运行承载层 Runtime / Transport

负责：

```text
Electron renderer
  -> preload / contextBridge
  -> PiBridge
  -> main
  -> MessagePort / TCP RPC
  -> agent-host
  -> handler
```

必须审计：

- 调用是否经过受控白名单桥；
- RPC 请求和响应是否可追踪；
- 超时、断连、进程退出、重启、重复请求的行为；
- Stream 事件是否可能丢失、重复或错配上下文；
- 不把测试 seed、fixture fallback 或运行时后门装进生产路径。

### 2.3 业务逻辑层 Domain / Use Case

负责：

- 前置条件和业务规则；
- 状态机和状态迁移；
- 权限、归档只读、幂等和重复提交；
- 成功时产生什么业务事实；
- 失败时是否回滚、是否可重试、是否允许部分成功。

### 2.4 功能模块层 Feature

按 S1-S7、对话、TTS、备份恢复、设置等模块分别审计：

- 模块自己的输入、输出和状态；
- 与其他模块的前置依赖；
- 依赖是通过明确 RPC / DTO / 事件传递，还是隐藏耦合；
- 一个模块产生的事实是否能被下一个模块真实读取；
- 是否出现“页面有按钮但模块没有可执行后端”或“后端有能力但没有用户入口”。

### 2.5 数据层 Persistence / Storage

负责：

- 业务事实的真实持久化；
- 事务、外键、约束、索引、WAL、连接关闭和恢复；
- SQLite 与文件存储的边界；
- 数据迁移、备份、恢复和重启回读。

### 2.6 测试与运维层 Test / Operations

负责证明：

- 代码、运行时、数据、错误和发布形态在目标环境中可复现；
- 测试证据类别不混淆；
- 安装、启动、重启、升级、备份、恢复和故障诊断有边界；
- 不把一次自动化通过误报为系统已经可运行、可验收、可运维。

## 3. 交互全集：先回答“用户到底能做多少种动作”

### 3.1 交互动作的定义

一个“交互动作”不是一个 DOM click，也不是一个 RPC 方法的简单别名。

应登记为：

> **用户意图 + 可见触发控件 + 当前上下文 + 业务状态变化 / 可观察结果**

例如：

- “在当前课程下创建一个学习任务”是一个业务动作；
- “点击按钮、输入标题、点击保存”是这个动作的多个 UI 步骤；
- “任务创建成功后刷新首页并在重启后仍可见”是该动作的验收结果；
- “重复点击保存”是该动作的并发 / 幂等负向路径，不另算一个业务功能，但必须有测试。

### 3.2 交互全集来源

从以下来源合并，不以某一个来源为准：

- `09-UI` 的 Tab、控件、交互说明和原型文字；
- `07-Workflow` 的学生主路径、状态机和跨模块路径；
- renderer 中真实存在的可操作控件；
- `06-API` 的用户操作 RPC；
- `04-Todo` 已完成任务和验收记录；
- T-M5-001 的 control inventory 和缺口登记；
- 安装后真实应用的逐页控件审计；
- 真实 Electron / 原生桌面 UAT 中可达和不可达的动作。

### 3.3 交互动作登记表

建立唯一交互清单，例如：

```text
H:\pi-studybuddy-tmp\runs\<task-id>\system-governance\interaction-catalog.md
```

每一行至少包含：

| 字段 | 要求 |
|---|---|
| `interaction-id` | 全局唯一，例如 `INT-S1-TASK-CREATE` |
| 用户意图 | 用学生能理解的中文描述 |
| 模块 / 页面 | S1-S7、对话、TTS、备份、设置或壳层 |
| 控件 ID | 对应 UI inventory；无控件则标记缺入口 |
| 触发方式 | 点击、输入、选择、拖拽、确认、重试、重启等 |
| 前置上下文 | 当前学期、课程、资料、考试、模块或权限状态 |
| 输入 | 用户输入及服务端校验边界 |
| 既有 RPC / handler | 精确到方法和 handler |
| 成功结果 | 用户可见结果和真实业务变化 |
| 错误路径 | 可预期错误、系统错误和恢复方式 |
| 禁用 / 只读 | 哪些状态下不可操作、为什么 |
| 重试 / 取消 | 是否支持、重试是否幂等 |
| 持久化结论 | 写入何处、写入什么、何时回读 |
| 重启验收 | 关闭再打开后应该看到什么 |
| 证据类别 | unit / integration / Electron E2E / native UAT |
| 当前状态 | verified / partial / missing / blocked |
| 任务归属 | 当前任务或后续 task-id |

### 3.4 交互数量的统计口径

最终必须给出多个不混淆的数字：

1. **业务意图数**：用户希望完成的独立业务动作；
2. **可见控件数**：页面中真实可操作或可触发动作的控件数；
3. **RPC 接口数**：支撑这些动作的契约方法数；
4. **负向状态路径数**：失败、取消、禁用、只读、归档、超时、重试、重复提交等；
5. **完整用户闭环数**：具备创建 / 使用 / 重启回查证据的动作数；
6. **未覆盖 / 不可达动作数**：不能用自动化通过数量掩盖。

不得用“127 个 RPC = 127 个用户动作”，也不得用“页面能渲染 = 交互已完成”。

## 4. 每个交互必须有统一行为契约

对每个 `interaction-id` 建立行为矩阵：

| 行为维度 | 必须回答的问题 |
|---|---|
| 初始 | 控件在无上下文时显示什么？ |
| 前置不满足 | 是隐藏、禁用、提示还是允许进入后失败？ |
| 输入校验 | 空值、格式、大小、范围、重复值如何处理？ |
| loading | 操作中用户看到什么？是否防重复点击？ |
| success | 成功事实是什么？页面如何刷新？ |
| partial success | 哪些结果已保存？哪些未完成？ |
| failure | 错误码、中文文案、归属层和下一步是什么？ |
| retry | 重试是否安全？是否重复创建或覆盖事实？ |
| cancel | 取消是否回滚？是否留下中间状态？ |
| timeout | 超时是否可继续、重试或重启？ |
| readonly | 归档或只读时 UI 和 host 是否双重阻止？ |
| race | 切换课程 / 学期 / 页面后旧响应会不会覆盖新状态？ |
| restart | 关闭并重启后哪些结果必须存在？ |
| privacy | DOM、日志和截图是否脱敏？ |
| evidence | 哪类测试真正证明了它？ |

**任何动作缺少其中一项，不得称为“完整闭环”。**

## 5. 错误治理：错误不是一句“操作失败”

### 5.1 错误分层

每个失败都必须标注“发生层”和“处理层”，至少覆盖：

| 层级 | 典型错误 | 责任边界 |
|---|---|---|
| UI 输入层 | 空值、格式错误、未选择对象、重复点击 | UI 尽早提示；不能替代服务端校验 |
| 运行承载层 | bridge 不可用、RPC 超时、断连、进程退出 | transport 统一转换；提供重连 / 重启语义 |
| 契约层 | 参数不符合 DTO、错误信封异常 | contract / RPC 层拒绝并保留稳定错误码 |
| 业务规则层 | 未确认考试、归档写入、状态机不允许 | handler / domain 负责事实判断和固定错误 |
| 持久化层 | FK、CHECK、唯一约束、事务、WAL 锁 | data layer 处理事务和脱敏错误；不能泄漏 SQL |
| 文件系统层 | 文件不存在、MIME 不符、大小超限、路径越界 | capability / storage / handler 校验和清理 |
| 工具链层 | OCR/WPS/whisper 未配置、超时、格式失败 | Adapter 返回可分类错误；不得猜路径或云端回退 |
| 模型 / 外部能力层 | 未配置模型、模型超时、响应格式错误 | 生产真实错误与确定性降级分开；不静默使用测试 fixture |
| 进程 / 运维层 | 启动失败、升级失败、数据根损坏、恢复失败 | 运维诊断、日志、重启、备份恢复边界明确 |

### 5.2 错误归属矩阵

建立：

```text
error-ownership-matrix.md
```

每个错误至少登记：

| 字段 | 要求 |
|---|---|
| `error-id` | 全局唯一，例如 `ERR-S5-EXAM-NOT-CONFIRMED` |
| 触发动作 | 关联 `interaction-id` |
| 发生层 | UI / transport / contract / domain / DB / file / tool / model / ops |
| 原始原因 | 技术事实，禁止直接展示给用户 |
| 统一错误码 | 与 `06-API` 对齐；未经裁决不得随意新增 |
| 用户文案 | 中文、可操作、不含路径 / UUID / 栈 / SQL |
| UI 状态 | error / retry / disabled / readonly / partial |
| 是否可重试 | 是 / 否 / 需修改输入 / 需重启 / 需配置 |
| 重试副作用 | 是否可能重复写入、重复任务、重复投递 |
| 回滚 / 补偿 | 事务回滚、幂等、人工恢复或无补偿 |
| 日志 allowlist | 允许记录哪些摘要 |
| 用户证据 | DOM / 截图 / JSON / 操作步骤 |
| 自动化测试 | 测试文件和断言 |
| 任务归属 | 当前任务或后续任务 |

### 5.3 错误处理的统一原则

- 低层错误不能原样穿透到 renderer；
- UI 不得吞掉失败、伪造成功或只显示空白；
- 错误消息必须告诉用户“发生了什么”和“下一步怎么办”；
- 可重试错误必须有可见且真实的重试入口；
- 不可重试错误必须说明修改输入、配置工具、重启或联系维护的边界；
- 业务事实写入失败时，不能把 UI 状态提前改成成功；
- 部分成功必须明确哪些已落库、哪些未落库；
- 每个错误至少有一个自动化断言和一个适用的用户路径证据；
- 生产路径不得把 mock、fixture、`test.*` seed 当作错误恢复。

## 6. 数据治理：先定义事实，再决定存 SQLite 还是文件

### 6.1 当前生产数据根必须以代码和 ERD 双重核验

当前设计基线记录了：

```text
生产业务根：%LOCALAPPDATA%\PiStudyBuddy
全局库：     %LOCALAPPDATA%\PiStudyBuddy\global.db
学期库：     %LOCALAPPDATA%\PiStudyBuddy\semester\<semester-id>\sem.db
L3 会话库：   %LOCALAPPDATA%\PiStudyBuddy\memory\l3\conversation.sqlite
L1 画像：     %LOCALAPPDATA%\PiStudyBuddy\memory\l1\learner-profile.json 等
L2 索引：     %LOCALAPPDATA%\PiStudyBuddy\memory\l2\wiki-index\
配置：       %LOCALAPPDATA%\PiStudyBuddy\config\
资料存储：   业务根下由 storage_key 指向的 storage/ 层级
```

这些是核验起点，不是跳过代码核验的理由。必须确认：

- `PI_STUDYBUDDY_DATA_ROOT` 是否只在测试 / 受控运行中覆盖业务根；
- 全局库与学期库的建立、打开、关闭和 WAL 生命周期；
- `global.db:semesters.db_relative_path` 与真实学期库是否一致；
- `storage_key` 是否只允许业务根内相对路径；
- `~/.pi` 是否保持与业务数据根物理隔离；
- 配置、凭证、记忆、资料原文、SQLite 业务事实是否各自落在正确边界。

### 6.2 数据分类

每个交互产生的数据必须归入以下一种或多种类别：

| 数据类别 | 判断问题 | 默认策略 |
|---|---|---|
| 业务事实 | 重启后学生仍认为它发生过吗？需要审计、统计、恢复吗？ | 必须持久化，通常 SQLite |
| 状态迁移 | 状态变更影响后续权限 / 工作流吗？ | SQLite + 约束 / 事件 |
| 用户输入 | 学生主动录入且未来要继续编辑吗？ | SQLite 或受控文件，必须有归属 |
| 资料元数据 | 文件名、类型、大小、hash、转换状态是否参与业务？ | SQLite |
| 资料原文 / 二进制 | 体积、格式和访问方式是否适合数据库？ | 业务根内文件；SQLite 存元数据和 `storage_key` |
| 派生结果 | 可由事实稳定重算且不需要保留快照吗？ | 默认不持久化或单独缓存，必须说明 |
| 快照事实 | 即使源数据变化仍必须保持当时结果吗？ | SQLite JSON / 文件快照 + hash |
| 运行态 | loading、当前页、临时输入、窗口焦点是否只在本次运行有效？ | 不写业务 SQLite |
| 缓存 / 索引 | 删除后可重建吗？ | 文件或缓存；必须有失效和重建规则 |
| 日志 / 审计 | 需要诊断但不应含隐私吗？ | 脱敏日志；不把日志当业务事实 |
| 测试数据 | 是否只为测试存在？ | 专用运行根；不得进入生产数据根 |

### 6.3 数据持久化登记表

建立：

```text
persistence-registry.md
```

每个数据对象至少登记：

| 字段 | 要求 |
|---|---|
| 数据对象 | 如任务、考试、作答、错题、笔记、资料元数据 |
| 来源交互 | 关联 `interaction-id` |
| 是否业务事实 | 是 / 否，给出理由 |
| 存储介质 | global.db / sem.db / L3 SQLite / JSON / storage file / memory |
| 真实路径 | 生产路径和测试路径分别写清 |
| 表 / 文件 | 精确到表名或文件相对位置 |
| 主键 / 外键 | UUID 关系和跨库引用边界 |
| 写入时机 | 创建、提交、完成、确认、归档或异步任务结束 |
| 事务边界 | 单事务、跨文件原子操作、补偿策略 |
| 更新规则 | 可编辑、追加、状态迁移、幂等或不可变 |
| 删除 / 归档 | 软删除、归档、物理删除和恢复规则 |
| 重启回读 | 用户能看到什么，如何验证 |
| 备份恢复 | 是否进入备份，恢复后如何验证 |
| 隐私等级 | 是否含资料原文、题干、答案、家长信息或凭证 |
| 当前测试证据 | 数据库断言、E2E、UAT 和日志路径 |
| 未决问题 | 需要用户或设计裁决的事项 |

### 6.4 绝不默认写入 SQLite 的内容

除非设计明确要求，下列内容不能因为“方便测试”就写成业务事实：

- UI 当前选中的 tab、输入框草稿、loading 状态；
- 可由源事实稳定生成的速背卡和冲刺计划；
- 单纯的 renderer 自动化结果；
- 测试 seed 标记、mock provider 响应和调试状态；
- 临时错误栈、完整模型输出或敏感原文日志。

反之，任务、考试确认、作答提交、练习结果、错题归档、学生确认的错因、笔记保存、学习状态迁移等如果会影响后续闭环，必须明确真实持久化位置和重启回读证据。

## 7. 全链路追踪：一个动作必须贯穿到数据和测试

建立唯一追踪矩阵：

```text
system-interaction-traceability.md
```

建议列：

| 交互 ID | UI 控件 | UI 状态 | PiBridge | RPC contract | main / host | handler / domain | SQLite / file | 错误码 | 自动化测试 | 原生 UAT | 重启回查 | 任务归属 |
|---|---|---|---|---|---|---|---|---|---|---|---|---|

每个交互必须能回答：

```text
用户做了什么？
系统经过了哪些层？
哪一层决定成功或失败？
产生了什么真实数据？
数据写到了哪里？
失败时谁负责转换错误？
重启后如何证明仍然存在？
哪条测试和哪份用户证据证明了它？
```

如果链路中任何一段只有静态按钮、未接线 handler、测试 fixture、隐藏 seed、未经声明的前端状态或未定义的数据落点，标记为 `missing`，不得标记为 `verified`。

## 8. 测试策略：真实数据、分层证据、不混淆 UAT

### 8.1 测试层级

| 测试层 | 允许 | 证明范围 |
|---|---|---|
| unit | mock 外部能力、纯函数、状态机 | 规则和局部错误语义 |
| integration | 真实 schema / handler / 专用 SQLite；外部服务 mock | 数据、事务、contract、业务层边界 |
| Electron E2E | 真实 Electron；测试根专用 SQLite；运行期走正式 RPC | 真实桌面运行链路和页面业务操作 |
| native UAT | 可见 OS 鼠标键盘；UI 创建前置数据；同根重启 | 用户实际可用性和完整创建→使用→重启闭环 |
| package / operations | 隔离安装、启动、重启、升级、恢复 | 运维和交付形态 |

### 8.2 测试数据库纪律

- 测试数据库只写 `H:\pi-studybuddy-tmp\runs\<task-id>\...`；
- 生产业务数据仍位于 `%LOCALAPPDATA%\PiStudyBuddy`；
- 数据库型测试使用真实 `global.db` / `semester/<id>/sem.db` schema、FK、CHECK、trigger；
- 如果某个前置实体没有公开 UI / RPC 创建入口，只能在真实 Electron 启动前建立专用测试库，并明确这属于自动化测试前置，不属于 UAT；
- 运行中的应用不得暴露 `test.*` seed RPC；
- 建库 helper 返回前关闭 SQLite 连接；Windows WAL / SHM 不得造成锁竞争；
- 不复制、查询、覆盖或污染真实业务数据根；
- 自动化中的 mock 业务数据不能伪装成用户真实创建的数据。

### 8.3 UAT 铁律

每个纳入任务的用户可见闭环必须尽可能执行：

```text
全新隔离根
  -> 可见 UI 创建前置数据
  -> 可见 UI 使用功能
  -> 可见 UI 观察成功 / 失败 / 重试 / 禁用
  -> 关闭应用
  -> 同一隔离根重启
  -> UI 回查持久化结果
```

`webContents.executeJavaScript`、CDP、直接 RPC、handler 直调、数据库预置和运行中 seed 都不能被称为原生真机 UAT。

若产品没有纯 UI 前置入口：

- 如实登记为 `not executable by current UI`；
- 形成范围裁决请求；
- 不把空态可达性称为完整闭环；
- 不自行加入测试后门来制造闭环。

## 9. “完整 phase”必须改成“完整垂直切片”

后续任何功能实现或缺陷修复，不能只交付前端或后端的一侧。一个交互动作只有在下面全部具备时才算完成一个**完整垂直切片**：

1. 需求意图和验收条件；
2. UI 控件和所有用户可见状态；
3. typed RPC / contract；
4. main / preload / host 运行链路；
5. handler / domain 规则；
6. SQLite / 文件持久化或明确“不持久化”结论；
7. 错误码、中文文案、重试、取消、幂等和恢复；
8. unit / integration 测试；
9. 真实 Electron E2E；
10. 适用的原生真机 UAT；
11. 重启回读、备份 / 恢复或运维影响说明；
12. 交互清单、错误矩阵、数据登记和实施记录同步。

任何一项缺失，都应写成 `partial` 或 `blocked`，而不是通过增加一个 phase 名称掩盖断裂。

## 13. 强制停止条件

出现任一情况，停止相关业务施工并报告：

- 交互动作无法关联到真实控件、contract、handler 或数据落点；
- UI 与后端的成功 / 失败语义不一致；
- 错误无法分类或需要新增公共错误码而未获裁决；
- 业务事实没有明确持久化位置；
- 测试依赖真实业务数据根、mock 伪造业务事实或运行时 seed；
- 只能通过 RPC、handler、数据库、CDP 或 `executeJavaScript` 完成所谓 UAT；
- 需要新增 API、schema、handler、Stream、全局状态或跨任务能力；
- 发现问题超出 T-M5-004 范围；
- 发现完整 UUID、绝对路径、密钥、SQL、错误栈或资料原文进入用户证据；
- 需要危险 Git 操作，或工作区存在无法确认归属的修改；
- 没有足够证据证明重启后业务事实仍然存在。

停止报告必须包含：

```text
已读取的权威文件与版本
live Git 状态
交互 / 错误 / 数据审计证据路径
触发的停止条件
对当前任务和后续任务的影响
推荐裁决方案
需要用户回答的唯一问题
裁决前不会执行的动作
```

## 14. 完成定义

本提示词资产完成，只表示系统测试阶段已经有了统一的审计语言和治理边界：

- 用户动作可枚举；
- 每个动作有统一行为契约；
- 错误有分层和责任归属；
- 业务事实与运行态 / 派生结果有持久化边界；
- SQLite、文件、配置、记忆和测试根的路径可核验；
- UI、运行、逻辑、功能、数据、测试运维职责可追踪；
- 自动化 E2E 与原生真机 UAT 不混淆；
- 每个完整交互以垂直切片验收；
- 超出当前任务的发现有明确裁决入口。

本提示词资产不表示：

- T-M5-004 已完成；
- 所有交互已验证；
- 所有错误已修复；
- 所有数据已持久化正确；
- 测试已经全绿；
- 原生真机 UAT 已通过；
- 任务已 done；
- Git 已提交、合并或推送。
