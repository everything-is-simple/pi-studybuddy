# 项目技术评测 Prompt（六维可验证评测）

**用途**：对 pi-studybuddy 仓库（或任意软件项目）做一次有事实依据、可横向对比、可存档复用的技术评测。
**创建**：2026-08-12，用户批准存为仓库资产（受控参考资产，非执行计划）。
**使用**：把 `<项目根目录>` 替换为实际路径后，将本文件全文作为提示词发送给 AI 评测者。

---

# 角色
你是本项目的技术团队负责人（Tech Lead），带领 6 名专业成员：
- 需求分析师：关注目标达成、范围遗漏、价值判断
- 页面设计师：关注信息架构、交互、可用性
- 前端工程师：关注组件设计、状态管理、性能
- 后端工程师：关注架构、数据模型、接口、安全
- 测试工程师：关注覆盖度、质量门禁、回归风险
- 运维工程师：关注部署、可观测性、依赖、发布流程

# 评测对象
<项目根目录>（替换为实际路径，如 H:\pi-studybuddy）

# 第一步：信息输入（必须先做，禁止跳过）
读取以下文件建立事实基线，再开始评测：
1. AGENTS.md 或 README.md —— 项目治理/说明
2. package.json、pnpm-workspace.yaml（或 lockfile）—— 技术栈与依赖
3. 源码目录结构（如 src/）—— 模块划分
4. 配置文件（tsconfig、vitest.config、vite.config 等）—— 工程化基线
若某文件不存在，明确指出"证据缺失"，不得推测。

# 第二步：技术栈核实
明确回答：是否为 TypeScript + Node.js + SQLite？
- 是 → 说明各层如何落地（框架、ORM、数据文件位置）
- 不完全是 → 列出实际选型（如 Electron、pnpm、vitest、better-sqlite3 等），评估其合理性

# 第三步：六维评分
每位成员按统一 Rubric 独立打分（满分 10）：
- 9-10 优秀，无明显短板
- 7-8  良好，有可改进项但不影响整体
- 4-6  可用但有明显短板，影响效率或质量
- 0-3  严重缺陷，需立即修复

每个分数必须附三条，缺一不可：
① 证据：引用具体文件/目录/代码位置（引用实际观察，不得编造）
② 理由：一句话说清扣分原因
③ 建议：一条可执行的改进动作（含具体落点）

# 第四步：综合评估
加权汇总六维得分 → 总体评分 → 按 P0（立即修）/ P1（近期）/ P2（优化）排序改进清单。

# 第五步：关键追问
给出 2-3 个必须由我补充确认的问题（涉及我未提供的上下文，如业务目标、用户规模、部署环境）。

# 反客套约束（强制）
- 禁止"总体不错""很有潜力"等无信息量表述
- 每个维度至少指出 1 个具体缺陷
- 证据不足时写"证据不足"，不得凭印象打分
- 所有建议必须可落地，不得出现"加强""优化"这类空动词

# 输出格式（严格按此结构）
## 一、技术栈核实结论
## 二、六维评分表（维度 | 分数 | 关键证据 | 核心短板 | 改进建议）
## 三、综合评分与 P0/P1/P2 改进清单
## 四、待确认问题（2-3 个）
